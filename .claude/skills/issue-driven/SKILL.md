# Issue 駆動開発（詳細）

**適用範囲は「実質的な開発」**＝機能追加・修正・リファクタ・バグ修正。作業を始める前に Issue が要る。

## 適用するか／しないか

| 除外（Issue 不要） | 適用（Issue 必要） |
|---|---|
| typo 修正 | 機能追加 |
| docs の微修正 | バグ修正 |
| `tmp/agent-status.tsv` の台帳更新 | リファクタ |
| 自明なワンライナー | 仕様変更 |

迷ったら**適用側に倒す**（後から Issue を作るより、着手前に作る方が安い）。

## 着手前

**GitHub Issue を書く**（既にあればそれを使う）。書くのは 2 つ：

1. **目的**（何のためか）
2. **チェック項目 `- [ ]`** を**作業単位に分解**したもの

> **着手前の Issue 作成は常設許可**。CLAUDE.md の「Issue 作成は本人判断」より**このルールが優先**する。着手のためなら確認を取らずに作ってよい。

## チェックリストは Issue 本文（先頭）に置く

**コメントに置かない。** 理由：

- 先頭に置けば常に可視（コメントは流れて埋もれる）
- 編集箇所が 1 つで済む（進捗の正本が分散しない）
- auto-close と相性が良い

既存 Issue（bug-watcher が起票したものなど）に**本文チェックリストが無ければ、本文を編集して追加**する。

**コメントの用途**は、方針変更・経緯・補足の記録。**進捗チェックの正本は本文に一本化**する。

## コミットのたびに更新

コミットが着地したら、**対応する Issue のチェック項目を `- [x]` に**する。

サブエージェント（coder 等）のコミットが着地した場合は、**司令塔が反映する**（各コミットが Issue のどの項目に当たるかを対応づけるのは司令塔の仕事）。

```bash
env -u GITHUB_TOKEN gh issue view <N> --json body -q .body > /tmp/body.md
# 該当行を - [ ] → - [x] に編集してから
env -u GITHUB_TOKEN gh issue edit <N> --body-file /tmp/body.md
```

### Issue に無い作業を入れてしまったら
**Issue にその旨を追記する**。具体的には**本文のチェックリストに項目を追加**する（経緯の説明が要るならコメントで補足）。

Issue と実装の乖離を残さない。「ついでにやった」を黙って通さない。

## Close の条件

**develop にマージされ、かつ全チェック項目が完了したら Close する。**

- master 到達時の auto-close を**待たない**（develop 止まりの期間が長いと、完了済みの Issue が開きっぱなしになる）
- **feature コミット単体（develop 未マージ）では閉じない**＝早すぎる Close を避ける

PR 本文の `Closes #N` は**保険**（master 到達での auto-close 用）。feature→develop と develop→master の**両方に書く**。→ 詳細は `git-flow` スキル。

## 実装済みが分かるように保つ

候補一覧のような**長い表を持つ Issue** では、チェックリストだけ更新しても表の側が古いままになる。表にも `✅` などの印を入れ、**どこを見ても同じ状態が読めるように**する。
